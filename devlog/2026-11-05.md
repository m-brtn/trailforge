## Problems and solutions

- **Two JSON forward declarations would clash with the alias.** `DriftScore.h` declared `tf::json::Value`; with
  `namespace json = quench::json;` in `tf` that is a redefinition. It now declares `quench::json::Value` and the alias.
- **`json::parse` changed its signature** (`Result<Value>` instead of a value and an error string). The tests' `CHECK`
  does not return, so test call sites use `valueOr({})` and check the result separately.
- **The first after-change `full_check` did not run:** in zsh a `rm -f /tmp/trailforge_*.png` without matches fails
  and stopped the `&&` chain (only `visual_tour` ran). Rerun with `null_glob`.
- **The pause logo differed by up to 23 levels** (0.288 % of the pixels of `07_paused`). Cause: the engine's ImGui
  sampler used Nearest mipmaps, ImGui's SDL GPU backend Linear. Fixed in the engine; afterwards `07_paused` differs
  in 0.001 % of the pixels.
- **The physics debug lines ("Draw on top") were hidden behind the car before.** Their pipeline had no depth target
  but drew in the scene pass, which has one; SDL's Metal backend then kept the previous pipeline's depth state. The
  port declares the depth format with test and write off, so the lines are drawn on top, as the option says. A
  behaviour change in a debug view that is off by default and in no scenario.
- **`perf_presets.txt` gave no usable A/B** (three alternating pairs): in two runs `set vsync` did not take effect
  (60 FPS in the no-vsync phases of one run, 103 FPS with vsync in another, once in each binary), and the CPU time of
  one binary switched between about 0.6 and 1.5 ms within a run (likely the core or clock of the main thread). Used
  instead: a temporary scenario with vsync on throughout (High, follow camera, overview, meadow, spray; 4 s each),
  eight alternating pairs.
- **Debug ctest `level_tile_streaming` failed once** under a parallel build (it sleeps on a worker thread); it passed
  alone and in both later Debug runs.
- **The last `full_check` captures differed more than the run before** (mean 0.057 against 0.020): in images 14 to 18
  one ImGui slider frame ("Front spring") was lighter by 9 to 21 levels, the hover colour; the real mouse pointer was
  over the window. The earlier run had no difference there.
- **The first iPhone run stopped after the pause capture** with a black screen and the process alive. The crash
  report of a `SIGABRT` sent to it showed the main thread idle in `UIApplicationMain` and no TrailForge thread left:
  `main` had returned without a scenario result. Cause: `devicectl` had been started in the background of a shell
  call that ended, and was killed with it; killing it terminates the app on the device, SDL turns that signal into
  `SDL_EVENT_QUIT`, and TrailForge leaves its loop silently. The same scenario under a `devicectl` that stayed alive
  ran to the end (25/0). Not caused by the renderer change.
- **On iOS the process outlives `main`:** after `SDL_main` returns, SDL's UIKit delegate keeps the run loop going and
  the app shows a black screen until it is terminated. This is why the app stayed alive after `ios_check` in the
  Simulator (open question of 04:04). The engine's app shell (SDL main callbacks, the next step) ends the app
  through `SDL_APP_SUCCESS` instead.
- **App shell: every scenario `tap` of a letter key did nothing** (at least 60 failed checks in `full_check`: Q,
  B, T, X, L, R, C, P, ...; held keys like W worked). Cause: the engine's scenario builds the keycode with
  `SDL_GetKeyFromScancode(scancode, SDL_KMOD_NONE, false)`, which gives the layout's letter (Cyrillic on this Mac's
  Russian layout), while real key events carry Latin letters there (SDL's `latin_letters` keycode option) and
  TrailForge's key actions match keycodes; the old runner passed `true`. Solution: `Application::event` recomputes
  the keycode of key events in scripted runs with `key_event = true`. The engine fix (pass `true` in `pushKey`,
  `src/app/AppScenario.cpp`) makes this unnecessary.
- **`ios-xcode` build failed: `src/app/main.cpp` not found.** The Xcode project was generated before the file was
  removed; `cmake -S . -B build/ios-xcode` (cached settings) regenerated it.
- **The first `full_check` after the keycode fix showed an ImGui tooltip** ("Friction ellipse") in `17_rocks` and
  `18_low_grip` (mean 0.96 and 0.99 against the run before, all other images at noise level). No scripted mouse
  command points there and no navigation highlight was drawn; the tooltip sat where ImGui places it for a hovering
  mouse. Cause: the real mouse pointer over the window. Rerun with the pointer moved to the screen's left edge
  before each run (a `CGWarpMouseCursorPosition` helper): no tooltip, mean 0.027.
- **`touch_drive` line 44 failed after the change** (`expect steer < -0.95`, actual -0.935; before -0.971 with the
  same old script and the build before the change). The vehicle steering is rate-limited (about 4.4 per s, 0.037 per
  tick), and since the change the check comes one tick earlier after `finger move` + `wait 0.3` (the input-timing
  shift under "Limitations"). Solution: `until steer < -0.95 0.1` (it follows within a few ticks); now 37/0, the
  `until` met at -0.971.

## Limitations and open questions

- The gates above ran with the pin `502c35e`; after the move to `dc22eeb` (same engine sources) only the Release
  build, ctest and one start were repeated.
- The iPhone was not used (no device run of this build). Windows and Linux were not built: CI is paused, and the
  engine has never been built with MSVC or GCC.
- Configure of the `headless` preset and of `tools/texc` now downloads the engine's shader toolchain sources
  (glslang, SPIRV-Tools, SPIRV-Cross; DXC on Windows) although nothing there compiles shaders; before, TrailForge
  included its toolchain only with `TRAILFORGE_BUILD_APP`. The toolchain is not built there. A fix belongs in the
  engine (include it only when a target needs it).
- In the Simulator the app stayed alive after the `ios_check` result line until the 600 s timeout of the check;
  earlier Simulator runs were stopped by hand as well. Not investigated.
- Packaged builds do not ship the libraries' licence texts (SDL, Jolt, ImGui, GLM, miniaudio, and now the engine,
  MIT, whose `THIRD_PARTY_LICENSES` lists them); `tools/release/` and `cmake/IosBundle.cmake` copy none. This predates
  the switch; it needs a decision before the next release.
- The headless test count before the change was not measured (only after: 104).
- The renderer port needs an engine with a public `ImGuiRenderer` and `ColorTarget::cycleResolve` (`3dfb9f4`). Its
  gates ran with the local engine checkout; from the pinned archive only Release ctest, a start and `visual_tour`
  were repeated.
- The port ran on the iPhone only with scripted input and the validation layer: no device frame times without
  validation, no device A/B against the original renderer (it never ran on the device), no real touch or controller.
  Not run on Vulkan.
- The CPU time spread between runs on this Mac is larger than a 5 % difference; the port shows no difference beyond
  it, which does not prove one below 5 %.
- Other changes in behaviour: a new log line at start (`[info] gpu: driver metal, device ..., shaders metallib`);
  failed submits and fences are now logged (before ignored); exception texts of resource creation failures changed.
  The spray fragment shader declares 3 samplers and uses 2, as before.
- `05_peaks_drive` in the Simulator is not deterministic, so it cannot show small rendering changes.
- App shell, behaviour changes: the engine runs scenario commands at the start of a frame, before `update`; input it
  pushes reaches the game one frame later, and after a `down`, `up` or `tap` the next command runs one frame
  earlier than before. Input TrailForge queues itself (`click_item`, `inputclick`, `touch_item`, `touchdrag`,
  `wheel_center`, `orbit`, `scrollto`, `mapclick`, `mapdrag`) keeps its old timing: such a command stays busy until
  its last event has been through a whole frame (one frame longer than "busy while pushing", or the next command
  would run before `update` saw the event). The level-pending gate holds only TrailForge's commands; the engine's
  `wait` / `until` / `expect` run during a level load. Unknown commands now fail when reached, not at load; a
  malformed `wait` / `until` / `expect` stops the run at load. Output: `scenario: ...` and `perf: ...` lines through
  the engine log (stderr) instead of `SCENARIO ...` / `PERF ...` on stdout; `SCENARIO telemetry` stays on stdout.
  Captures are PNG only. The exit summary is printed on every exit. The virtual gamepad's triggers rest at the minimum
  on attach. Engine `ticks` is the engine's clock; TrailForge's physics ticks are `sim_ticks`.
- Debug builds no longer turn on GPU validation by themselves (`--gpu-debug` does; the engine has no `AppDesc`
  default for it). `--present-mode` acts only while the VSync setting is on, and the perf line's `vsync=` reports
  TrailForge's setting (the engine has no getter for the present mode).
- On iOS the frames follow SDL's display link: 60 Hz in the Simulator (before about 120). TrailForge's `Info.plist`
  lacks `CADisableMinimumFrameDurationOnPhone` (the engine's template has it), so a ProMotion iPhone should stay at
  60 Hz as before; not run on the device since the change. Run on the iPhone at 16:46 with the key added: 120 Hz
  (frame p50 8.333 ms, "Results").
- Not run since the change: 26 of the 33 edited scripts, `audio_check` / `skid_check` with audio, Vulkan, the iPhone,
  `package_macos.sh` (its smoke check now looks for "app: quit after"), Windows and Linux CI. No CPU A/B against the
  build before the change (that binary was rebuilt). The iPhone: run at 16:46 (`ios_check` and a frame-time script).
- Engine fix wanted: scenario key events with `SDL_GetKeyFromScancode(..., true)` (see "Problems and solutions");
  TrailForge's workaround in `Application::event` can go then. Until then ImGui still receives the engine's
  layout keycodes for scripted letter keys (only `tf::Input` sees the corrected ones); no scenario depends on it.
  Done 15:25 (engine working tree, not committed): the workaround is removed, and ImGui now gets the same keycodes.
- `landing_audio` (line 70, the SUV does not climb from `place 26 -7.5`) and `spray` (lines 19 and 43, thresholds
  just missed) fail before and after the change: open, not caused by it. iOS 120 Hz with the new `Info.plist` key
  needs a device run. Done 16:47: 120 Hz on the iPhone.
- More behaviour changes of the app shell: an unknown flag exits with 1 (before 2); `--capture` without `--script` now
  runs deterministic frames (one fixed step per frame, never faster than real time), so `--capture-at` and
  `--quit-after` take longer in real time when frames are slower than 1/120 s; the HUD's FPS / frame-time line in
  scenario captures showed 72 FPS where the reference showed 60 (real timing, not deterministic in either binary).
- TrailForge keeps its own `FixedStepClock` and `stepSimulation` inside `update()` (pause, step once, menus that stop
  the simulation, audio per tick) instead of `Game::fixedStep`, to keep its behaviour; the engine's clock only sets
  the frame time. A follow-up.
- iPhone run of the app shell (16:46): one run of each script. The frame-time region without validation had the
  vehicle parked at the proving ground spawn (Low preset, no driving), so it shows the display rate, not the cost of
  driving; the driving regions of `ios_check` ran with validation on. Only `ios_check` ran on the device; real touch
  and a real controller are still untested there. What the screen showed: user report (16:52), everything on the
  screen looked normal and the apps closed by themselves.
